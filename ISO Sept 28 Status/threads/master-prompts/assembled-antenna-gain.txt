THE ARCHITECTURE YOU PLUG INTO
One estimator, run as four stages:
1. The core filter runs from the 18:01 prior (or an 18:22 prior) through the SATCOM data. For the integrated estimate it stops at 00:11, and the hand-off resamples its posterior, with each trajectory's full state, as the starting distribution for stage 2.
2. An end-of-flight stage continues each trajectory:
   - powered flight on the core dynamics until the end-of-flight module takes over;
   - the module simulates descents to impact;
   - the runner scores whichever 00:19 messages the config selects.
3. Impact-level modules each return a log-likelihood per impact sample.
4. A composer combines any chosen set of modules into one posterior. It reports evidence, effective sample size (ESS) and replicate agreement, and writes summary.json for the report. Results are shown per end-of-flight hypothesis first; any average across them appears only beside a prior sensitivity.

The hook API is on branch core/stages (crates/hypothesis/src/lib.rs), reviewed but not yet merged to main. Read it there with `git -C /jackbox/home/MH370 show core/stages:crates/hypothesis/src/lib.rs`. Develop on your branch from main and adapt to it; don't merge anything from core/stages yourself.
- In the filter: adjust_prior (and adjust_stratum_prior), extra_epochs, epoch_log_likelihood and final_log_likelihood, with StateView.
- After it: impact_log_likelihood(impact, choice) and predict(impact, out) per impact sample, with ImpactView (time, position, ENU velocity, flight-path angle, mass, total and vertical kinetic energy, descent family, takeover time and place, mode, alternative); or the Terminal trait for the end-of-flight module.
- Declarations: observations() (the observation IDs you consume, each used once per run, e.g. "m0019a.bfo"), alternatives() (discrete choices with priors; an alternative shared across modules is declared by the same name and marginalised jointly), absolute_scale() and prediction_columns().

Composition rules every module follows:
1. Return the likelihood of your data given the state, never a posterior. Remove any internal reference prior yourself. Say whether your likelihood is on an absolute scale; only absolute-scale likelihoods can be mixed across alternatives.
2. Each observation is used once per run. List the observation IDs you consume.
3. All impact modules use the same impact samples. Never smooth privately over impact location: the product of separately smoothed likelihoods is not the smoothed product.
4. Likelihoods must be smooth, with explicit model error. No floors. "Not computed" (NaN) is not "impossible". Cover the prior's support or refuse.
5. Be accurate where the other evidence is: where the flight posterior has its mass, roughly 30–40°S along the 7th arc, not only near your own peak.
6. Measure Monte Carlo adequacy (ESS, split-half replicate agreement). Report unconverged results as unconverged; the fix is the sampler, never smoothing.
7. Settle discrete model choices by evidence, or show them as labelled sensitivities. Never use fixed-weight averages of normalised maps.
8. Include one synthetic-recovery test (generate your data from a known state and check coverage), plus hand-computed fixtures.

The SATCOM logs carry received power for the R1200 bursts. A path predicts a received-power departure from:
- the aircraft's attitude: heading, pitch and roll;
- the satellite's direction;
- the installed antenna's gain pattern.
A likelihood compares that prediction with the logs. This is directional information that BTO and BFO don't carry.
