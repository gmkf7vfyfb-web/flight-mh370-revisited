+## 2. Root causes
+
+1. **R1 – Definitions are in many places.** Meanings of files, columns, layers, bands and constants are in many READMEs, notes and papers. Agents guess meanings from names (F8, F6, F9).
+2. **R2 – Rules are prose, not code.** Physical checks (band, land path, coupling ≤ 1, known events, airgun shots) and wording rules depend on agent memory. Nothing stops a bad result before it gets to Pete (F5, F6, F7, F11).
+3. **R3 – Long threads and summaries lose information.** The module thread had 3,413 messages. Compaction summaries and parallel tracks dropped caveats and Pete's instructions. A summary changed a proposal into a rule (F4, F9, F14).
+4. **R4 – The brief is too large and has rules that are old or that conflict.** For example, "never ask, record gaps and continue" conflicts with "stop if data is missing" (F3, F4).
+5. **R5 – The set-up gives more value to output than to correctness.** "Keep going, do not stop" made agents use stand-ins and continue past missing inputs (F1, F3).
+6. **R6 – The agent checks its own work.** The same context that made an error also checked for that error. The review thread made new errors in the same way (F8, F10, F12).
+7. **R7 – The agent applies a method to MH370 before it shows that the method works on known events.** The detector, TL and timing were not validated on real arrivals first (F13, F12).
+
+The model is not the main cause. The same failures occurred on Fable 5.1 and on Opus 5.5. The causes are structural. A model change alone does not fix them.
+
+## 3. The solution
+
+The solution has six parts. Each part is directed at one or more root causes.
+
+### 3.1 Clean start (R3, R4)
+
+1. Put a tag on the current module branch (`hydro-archive-2026-10-23`). Do not delete anything.
+2. Move all hydroacoustic notes, charts and exchange products from 7–22 Oct to an `archive/` folder. Put one README in that folder. The README says that these items are not results.
+3. Make a new module folder with a clean structure (section 3.2). Only items that pass an entry test (section 3.4) go into it.
+4. Remove the wrong and superseded hydroacoustic rows from project memory. Keep Pete's rulings in one decisions log (3.5).
+5. Replace the HYDROACOUSTIC_MODULE profile with a short profile (3.5).
+
+This is not an audit. The archive keeps the old work. The new module accepts an old item only when a test shows that it is correct.
+
+### 3.2 One data registry, read by code (R1)
+
+1. Make one file, `registry.yaml`. Each input has one entry: path, sha256, units, valid frequency band, time base, definition, source of the definition (quoted, with page), and one second-source check value.
+2. Examples of entries: IMOS records per logger, Kadri Fig. 9 digitised traces, Royer event table and figure marks, airgun shot template, TL tables, GEBCO, WOA23, run J impact columns, the composer and Pléiades layers, the searched-area fields, the coupling anchor.
+3. Analysis code reads data only through a registry loader. The loader refuses a file or a column that is not in the registry. The loader refuses a file whose sha256 does not agree.
+4. Constants (the coupling anchor, pick sd, sound speed, clock offsets) are in the registry only, each with its source. If the source is not known, the entry says "no located source", and every result that uses the constant shows that text.
+5. Each product records the registry version that made it. When a constant changes, a script lists all products that are now out of date. This stops F9.
+
+### 3.3 Physics and wording gates, in code (R2, R5)
+
+The pipeline applies these gates to every candidate signal. Each gate gives a column with a verdict and a reason. Code makes the candidate register. The agent does not write it by hand.
+
+| Gate | Test |
+|---|---|
+| G-band | Band is inside the receiver passband (IMOS ≥ 8 Hz; Kadri traces ≥ 5 Hz; IMS below 31.5 Hz flagged as not calibrated). |
+| G-receiver | Receiver gives information (for example, Scott Reef 3250 is excluded, with the reason). |
+| G-airgun | At Diego Garcia South, distance in time to the nearest airgun shot, against the chance rate. |
+| G-path | The geodesic path from the source to the receiver does not cross land in GEBCO 2026. The path is not blocked (H08N, Chagos). |
+| G-time | The arrival is not before the earliest possible arrival at the maximum sound speed. |
+| G-known | Match against known events: Royer's 20 events and figure marks, the CMST event, and other catalogue events. |
+| G-energy | Coupling that gives the recorded level, at the q99 run J energy at that place. Ladder against the Metz anchor: ≤ 10× feasible, 10–100× strained, > 100× not feasible, η > 1 impossible. (This ladder is a proposal. Pete must rule on it.) |
+
+A wording check runs on every note and caption before Pete sees it. It stops forbidden words ("no signal", "confident", "all searched", "closed access", "not held", "definitely"). It requires the permitted forms, for example: "no transient was above the pre-registered false-alarm level; power at the predicted level was X; 95 % upper limit Y".
+
+### 3.4 Entry tests for work that we keep (R6, R7)
+
+The new module keeps old work only when a coded test passes. The test compares the item with an independent source. Work that passes is not done again. This prevents unnecessary rework.
+
+| Item to keep | Entry test |
+|---|---|
+| IMOS 3315 processing (time base, clock correction, calibration) | Reproduces CMST 2014 Fig. 1. The record says −0.7 dB and +2.4 s; the test recomputes it. |
+| IMOS RAM TL grid (31.8 CPU-hours, expensive to make again) | sha256 agrees. Spot values agree with an independent RAM run at 3 points per logger. |
+| KRAKEN/RAM TL for IMS paths, air9 validation | air9 residuals recomputed from the stored inputs. |
+| Metz F-35A coupling anchor 2.26e-3 | Independent recomputation from the paper's numbers (page cited), done by the verifier (3.6). |
+| Kadri Fig. 9 digitised traces | Overlay on the page image. Time axis checked at 3 tick marks. |
+| Royer event marks and table | Spot check of 5 events against the page images. |
+| Airgun shot template (H08S) | Shot interval and level histogram agree with the 10 Oct chart. |
+| Run J impact energy and time | Quantiles recomputed from the exchange columns, with their README definitions quoted. |
+| GEBCO/WOA23 readers | Known depth and sound speed values at 3 points. |
+
+Items that are not in this table (for example, candidates A–F, ranked tables, run-j-gated-v2, Kadri package v2) are not kept as results. The new pipeline makes them again from tested inputs. Candidate A becomes a named lead that the new pipeline tests. It is not a result.
+
+### 3.5 The agent: short rules, one decisions log, short sessions (R3, R4, R5)
+
+1. **Profile.** The new profile is short (about 1,000 words). It contains only hard rules:
+   - Read the registry and the decisions log at the start of each session.
+   - Do not use data that is not in the registry.
+   - If an input is missing, stop that part and tell Pete what is missing and where you searched. Do not use a stand-in without Pete's approval.
+   - Send results only through the pipeline and after the verifier (3.6).
+   - Give compute time, where it runs and development time before each run. Wait for Pete's approval.
+   - Use STE100 and Pete's chart rules.
+2. **Decisions log.** One file, `decisions.md`. It contains only Pete's rulings, with his words quoted, the date and the message. Agent proposals go in a separate file, `proposals.md`, until Pete approves them. This stops F14.
+3. **Work cards.** Each piece of work starts as a card: question, registry inputs, method, acceptance test, compute estimate, expected output. Pete approves the card. The work ends with a result card that starts with the check table.
+4. **Short sessions.** One session does one to three cards. The state is in the repo, not in the conversation. A new session starts at each milestone. This prevents long threads and compaction loss.
+5. **Parallel work.** Parallel tracks are allowed only for mechanical compute with fixed registry inputs and a coded acceptance test (for example, TL tiles). Analysis and interpretation stay in the main session. Pete decides the number of parallel tracks for each card.
+6. **Unattended runs.** An unattended run does only approved cards. At a missing input, it stops that card and continues with the next approved card. It does not invent work.
+
+### 3.6 Independent verification (R6)
+
+1. Before a result goes to Pete, a separate verifier agent checks it. The verifier has a fresh context and its own instructions ("find errors"). It gets only the result card, the code, the registry and the raw files.
+2. The verifier recomputes each key number with its own code from the raw files. It checks each chart against the data. It checks that each statement agrees with the numbers.
+3. The result card shows the verifier's report. If the verifier and the agent do not agree, Pete sees both values.
+4. Cost: about 20–30 % more tokens for each result (estimate). It is much less than the cost of a wrong result that goes downstream.
+
+## 4. The analysis programme
+
+This is the science work. It goes from first principles: impact PDF, feasible energy, feasible coupling, then the data. Each method is validated on known events before it is used on MH370.
+
+| Step | Work | Output | Compute (estimate) | Where | Development (estimate) |
+|---|---|---|---|---|---|

+| 1 | Entry tests for kept work (3.4) | Pass/fail table with reasons | 30–60 min | 2 threads | 3–5 h |
+| 2 | Method validation on known events: Royer's 20 events, CMST 01:34 event, air9, F-35A, San Juan. Detector P_D and false-alarm rate on real arrivals. TL level, slope and shape residuals. +| 3 | Feasible energy range (run J) and feasible coupling range (theory and prior examples; the examples that were not used are listed with the reason) | One table and one chart, with sources | minutes | 2 threads | 2–3 h |

+| 5 | For each feasible candidate: location posterior with propagated bearing, timing, clock and sound-speed uncertainty; the coupling that the recorded level implies; what the other stations should then show against what they show; searched-area share; Pléiades-conditional share | One result card for each candidate | < 1 h | 2 threads | 3–5 h |

+Pete approves each step before it starts. Each step delivers one verified result, not a batch of charts.
