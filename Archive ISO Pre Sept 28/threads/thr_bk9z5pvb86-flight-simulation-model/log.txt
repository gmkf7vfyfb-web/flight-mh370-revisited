# Design assessment

The canonical estimator does not currently contain an aircraft flight simulator. It uses a model-conditional, one-turn kinematic trajectory with optional wind and magnetic-heading corrections. Production runs presently use the simpler no-environment form. The 00:11–00:19 continuation freezes the inferred kinematics, and the end-of-flight model is either no displacement or a stochastic geographic offset—not a descent simulation.

The smallest credible progression is:

1. Preserve the current model as an exact low-fidelity control.
2. Add a transparent, in-process 3-DoF point-mass/energy model in the existing dynamics spoke.
3. Use 6-DoF software and any Boeing engineering-simulator access offline for validation and response-surface construction, not inside the particle likelihood.
4. Introduce the new transition first after the 00:11 posterior, where it runs once per particle, before considering changes to the full accident inference.

No files were changed, software installed, services purchased, or expensive simulations run. No secondary agent performed integration work; Core Analysis remains the sole integrator.

### Physical state inventory

Present, though sometimes only nominally:

- Time, geographic position, altitude, true track, ground speed.
- Vertical-speed storage, but the accident model sets it to zero.
- Mach as a static trajectory parameter, not evolving state.
- Heading as a derived trajectory output when environmental modes are enabled.
- A lateral-mode configuration label, not an autopilot or flight-control state.
- BFO bias, which is an estimator nuisance state rather than an aircraft systems state.

- Hydraulic systems, pumps, pressure, actuators, or control authority.

- Angular rates \(p,q,r\), angular acceleration, and moments.
- True airspeed as persistent state, body-axis velocity, angle of attack, sideslip, acceleration, or load factor.
- Lift, drag, thrust, aerodynamic coefficients, stability derivatives, or an operating envelope.
- Flight-control surface positions, commands, rate limits, saturation, trim, or control laws.
- Autopilot, autothrottle, FMS, vertical mode, speed mode, or mode transitions.
- Landing gear, flaps, slats, spoilers, structural state, terrain, or water-contact state.

## Recommended multi-fidelity design

| Fidelity | Purpose | Recommended placement |
|---|---|---|
| 0 — current kinematics | Reproducible baseline and limiting-case control. Preserve exact results. | Canonical inference control. |
| 1 — transparent 3-DoF point mass | Integrate WGS84 position, true airspeed, heading/track, flight-path angle, mass, usable fuel, lift/drag/thrust, wind, gravity, and fuel flow. Structural engine/guidance assumptions remain explicit scenario families. | In-process Rust in the existing dynamics spoke. First use after 00:11. |
| 2 — audited 6-DoF | Attitude, angular rates, moments, control surfaces, propulsion/tanks, and supported systems. | Offline recreation and validation under `.sources/`; never subprocess-per-likelihood. |
| External reference — Boeing engineering simulator | Compare terminal behavior with the simulator family used for the public Boeing cases. | External validation only unless automation, inputs, rights, and reproducibility are resolved. |

Tier 1 is the smallest model that can connect fuel, energy, descent, wind, and SATCOM kinematics causally. It should not manufacture detailed electrical or hydraulic values. Where systems affect dynamics, represent them as separately reported structural scenarios backed by evidence—for example, a particular propulsion-availability or guidance-availability condition. Do not average those families unless defensible prior probabilities become available.

A 3-DoF model cannot reproduce phugoid attitude motion, rotations, or control-surface/system transients. Those belong in Tier 2 or in a reduced terminal response model validated from sufficiently documented 6-DoF cases. The ten current Boeing trajectories are too sparse and incompletely specified to train such a response model by themselves.

## Proposed typed transition interface

A fidelity-tagged state avoids filling unsupported fields with misleading defaults:

```rust
pub trait FlightTransitionModel: Sync {
    fn descriptor(&self) -> &ModelDescriptor;

    fn propagate(
        &self,
        request: &TransitionRequest,
        sample_times: &[ModelTime],
        output: &mut [ObservationKinematics],
    ) -> Result<TransitionResult, TransitionError>;
}

pub struct TransitionRequest {
    pub initial: FlightDynamicState,
    pub scenario: StructuralScenario,
    pub commands: CommandSchedule,
    pub atmosphere: EnvironmentForcing,
    pub parameters: AircraftParameters,
    pub latents: TransitionLatents,
}

pub enum FlightDynamicState {
    Kinematic(KinematicState),
    PointMass(PointMassState),
    RigidBody(RigidBodyState),
}

pub struct PointMassState {
    pub time: ModelTime,
    pub position: GeodeticPosition,
    pub true_airspeed: Speed,
    pub true_track: Angle,
    pub flight_path_angle: Angle,
    pub mass: Mass,
    pub usable_fuel: Mass,
    pub propulsion: PointMassPropulsionState,
    pub guidance: GuidanceState,
}

pub struct TransitionResult {
    pub terminal: FlightDynamicState,
    pub events: Vec<FlightEvent>,
    pub diagnostics: IntegrationDiagnostics,
    pub provenance_digest: Digest,
}
```

Interface rules:

- `ObservationKinematics` projects only the position and velocity quantities required by SATCOM. SATCOM must not depend on dynamics-private mass, engine, or control types.
- The runner selects the model, obtains environmental forcing, and composes spokes. A dynamics model must not read another spoke’s files or global state.
- Every stochastic quantity is supplied in `TransitionLatents`, sampled by the particle engine. The simulator receives no RNG and has no hidden randomness.
- Unsupported state is explicit in the fidelity variant; it is not silently zeroed.
- Out-of-envelope operation, missing provenance, trim failure, or numerical non-convergence returns a typed failure. Extrapolation is never silently clamped.
- Ground contact and flameout are ordered events with interpolated event times, not solver errors.
- The descriptor records represented state, validity domain, model/data hashes, license, source applicability, and deterministic settings.

## Particle-inference runtime strategy

The accident estimator currently uses the static tempered interface, [`StaticModel`](/jackbox/home/MH370/crates/particle-filter/src/tempered.rs:25), which recomputes the complete trajectory likelihood for every mutation proposal.

The inspected run used 10,000 particles, 23 temperature steps, and eight mutation steps. Because the final temperature does not mutate, that is approximately:

`10,000 × (1 initial + 22 × 8) = 1.77 million`

complete likelihood evaluations per seed. The evidence is in the [production tempering configuration](/jackbox/home/MH370/configs/accident-production.toml:32), [tempering loop](/jackbox/home/MH370/crates/particle-filter/src/tempered.rs:173), and [stored run summary](/jackbox/home/MH370/runs/mh370/through-0011-medium-assessment/suite-summary.json:17).

Therefore:

1. Do not invoke JSBSim, Boeing software, Python, or any external process inside `log_likelihood`.
2. First run Tier 1 once per retained 00:11 posterior particle, then importance-reweight at 00:19 and report ESS. This is the cleanest direct comparison with the existing continuation.
3. Keep Tier 1 in-process, fixed-step or event-driven, allocation-controlled, and benchmarked.
4. Run Tier 2 offline over a designed parameter grid. If justified, build a transparent lookup/sparse-grid approximation with held-out error and explicit model discrepancy.
5. Never disguise emulator or model-family disagreement as measurement noise.
6. Only after Tier 1 proves necessary and fast enough should Core Analysis consider moving it into the full static likelihood or adapting the existing sequential [`ParticleModel`](/jackbox/home/MH370/crates/particle-filter/src/model.rs:21), which propagates state once between observation epochs.

## Validation requirements

Before accident inference:

- Zero wind and constant speed must reduce to the current WGS84 propagation.
- Fixed-altitude trimmed flight must have negligible energy and force residuals.
- Mass must be monotonic, fuel non-negative, and fuel exhaustion an exactly located event.
- Zero thrust, zero drag, and level-flight limits need independently calculated solutions.
- Coordinate-frame, sign, time, and unit tests must be independent of the implementation.
- Repeat at successively smaller integration steps and record state/endpoint convergence.
- Identical seed/configuration must produce identical artifacts at one and multiple thread counts.
- Existing BTO/BFO scalar fixtures must remain unchanged when fed identical kinematics.
- The held-back MH371 control can test ordinary powered-cruise behavior, but cannot validate abnormal end-of-flight dynamics.

### Public Boeing cases

The pinned recreation reports ten terminal trajectories. Its audit identifies cases 03, 04, 05, 06, and 10 as high-rate cases and derives 4.707–7.974 NM from the first 15,000-fpm threshold crossing to the final recorded point. However, the records terminate roughly 473–1,131 ft above the datum and do not identify water contact, probabilities, geographic orientation, seventh-arc alignment, or complete scenario inputs. See the [source recreation](/jackbox/home/MH370/.sources/iannello-high-rate-descent-before-seventh-arc/README.md:1) and [case data limitations](/jackbox/home/MH370/inputs/evidence/end-of-flight-public-cases.json:48).

ATSB reports that Boeing varied selected speed, fuel, electrical configuration, altitude, and turbulence, using the same aerodynamic model as a Level-D simulator and high-fidelity systems. It also cautions that the runs do not cover every scenario and can leave the aerodynamic database’s validated region. [ATSB MH370 investigation material](https://www.atsb.gov.au/investigations/ae-2014-054)

Consequently, current validation can only compare features and envelopes:

- Descent-rate threshold timing and maximum descent rate.
- Phugoid period/amplitude where observable.
- Rotation sense only after axes and orientation are established.
- Along/cross displacement from a common declared threshold.
- Duration and distance after the documented flameout event.
- Numerical stability under out-of-envelope operation.

Pointwise reproduction requires the original input deck: exact aircraft/engine configuration, initial mass and CG, fuel by tank, unusable-fuel rules, engine/APU states, electrical/hydraulic configuration, trim and autopilot state, turbulence realization, local axes, integration settings, model/software revisions, and output filtering. The cases must remain separate conditional cases; the repository has no basis for assigning probability weights.

Public Boeing airport-planning material can bound dimensions and published design weights, but it describes general planning characteristics, not accident mass, aerodynamic derivatives, control laws, or terminal dynamics. [Boeing 777 airport-planning document](https://www.boeing.com/content/dam/boeing/v2/airports/acaps/777-200-200ER-300_Rev_E.pdf)

## Simulator, provenance, licensing, and cost

- **JSBSim:** The official documentation describes a configurable C++ flight-dynamics kernel with mass balance, propulsion, fuel tanks, aerodynamics, flight controls, autopilot, systems, attitude, and batch scripting. It is LGPL-2.1. Official maintainers also caution that named commercial-aircraft models based on public information are approximations. It is a suitable offline kernel, but no community “777” file should be treated as Boeing evidence without a coefficient-by-coefficient provenance audit. [JSBSim documentation](https://jsbsim-team.github.io/jsbsim/python/index.html), [official repository](https://github.com/JSBSim-Team/jsbsim)

- **OpenAP:** Potentially useful as an independent nominal point-mass comparator; its public APIs expose drag/thrust and fuel-flow models based on open and ICAO-derived data. Exact aircraft/engine coverage, coefficient provenance, and LGPL-3.0 implications must be audited first. It is not needed as a canonical runtime dependency. [OpenAP documentation](https://openap.dev/drag_thrust.html), [official repository](https://github.com/TUDelft-CNS-ATM/openap)

- **EUROCONTROL BADA:** Useful only as a nominal-envelope comparator if access is approved. The official guide says licenses have no fee, but eligibility and use are restricted, BADA 4 access is not guaranteed, and the data may not be used to validate another aircraft model. That makes it unsuitable as an open canonical validation dependency. [BADA overview](https://www.eurocontrol.int/model/bada), [access guide](https://www.eurocontrol.int/sites/default/files/2024-09/eurocontrol-user-guide-bada-access.pdf)

- **Boeing engineering simulator:** No official public price or general access mechanism was located in the inspected Boeing/ATSB material. Before any purchase or engagement, ask about model and firmware versions, scenario-automation API, deterministic reruns, engineering support, data export, input-deck disclosure, redistribution, publication rights, and whether outputs may be committed or merely summarized.

For every coefficient, table, or state transition, require:

- Exact source and page/table/record locator.
- Aircraft and engine applicability.
- Units, reference frame, sign convention, time basis, and interpolation rule.
- Version and integrity hash.
- License and redistribution conditions.
- Valid operating domain and extrapolation behavior.
- Measurement/model status and uncertainty.
- Independent calculation or validation fixture.

## Recommended integration sequence

1. Keep the current one-turn implementation and stored outputs as the exact low-fidelity control.
2. Specify the transition types and provenance schema; add a future adapter around the existing kinematic model before changing equations.
3. Implement Tier 1 within the existing dynamics spoke, initially against limiting cases and known-flight controls—not against the accident posterior.
4. Add any needed pressure/density forcing explicitly. Do not silently infer a “measured atmosphere” from the current temperature/wind cube.
5. Apply Tier 1 to the 00:11 posterior once per particle and compare endpoints, BTO residuals, ESS, runtime, and failure rates with the frozen continuation.
6. Run propulsion, guidance, electrical-availability, or terminal alternatives as separately named structural families.
7. Recreate an audited 6-DoF model under `.sources/`, validate its public Boeing-case features, and quantify its domain failures.
8. Only with adequate case inputs should a transparent terminal response table enter the canonical end-of-flight spoke.
9. Reassess full-likelihood or sequential integration only after the post-posterior experiment demonstrates material scientific value.

## 1. Precise definition of the canonical estimator

The canonical estimator is the repository’s single supported deterministic mapping:

```text
(code revision,
 Estimate configuration,
 exact input hashes,
 model-family selection,
 seed set,
 execution settings)
    ->
(posterior particles,
 likelihood/evidence diagnostics,
 convergence data,
 manifest,
 generated reports)
```

An implementation is canonical only when:

1. It is reachable through the current runner’s [`Estimate` command](/jackbox/home/MH370/crates/runner/src/main.rs:37).
2. It is the one current in-place Rust implementation—no numbered or parallel “final” version.
3. The runner owns configuration, deterministic setup, spoke selection, inference orchestration, and outputs.
4. Scientific equations live in narrow typed spokes selected explicitly by configuration.
5. Every included or omitted evidence source is declared in the result.
6. Inputs, configuration, seed, executable/revision, and outputs are identifiable and reproducible.
7. The implementation has focused controls and an end-to-end deterministic check.
8. Product code does not import `.sources/` recreations.

That definition follows the repository contract in [AGENTS.md](/jackbox/home/MH370/AGENTS.md:3).

Important distinctions:

- The **canonical estimator** is the mechanism and output contract.
- The **canonical production baseline** is one selected configuration, currently [`accident-production.toml`](/jackbox/home/MH370/configs/accident-production.toml:1).
- A **canonical result** is conditional on its named model family, configuration, and evidence. It is not an assertion that the model is physically complete or that its mean is the true crash location.
- `ContinueToContact` and `AnalyzeFinalBfo` are supported controls/secondary analyses. They do not alter the core posterior unless Core Analysis explicitly integrates their likelihoods into `Estimate`.
- JSBSim experiments, paper recreations, and alternative route studies remain supporting evidence until their smallest justified method is reimplemented in a canonical spoke.

### Two important scientific cautions

First, ideal LNAV to the geographic South Pole is nominally degenerate with exact `ConstantTrueTrack(180°)` in the present deterministic model: both follow the activation longitude due south. They become distinguishable only through path-capture behavior, navigation disturbances, or cross-track recovery. They must not be counted as two independent pieces of model support merely because their labels differ.

McMurdo and a dated magnetic-pole coordinate do produce curved great-circle courses and are genuinely distinct.

Second, these destinations were selected as specific hypotheses after inspection of available evidence. Comparing their conditional fit is sound; comparing Bayesian evidence against a free 0–360° post-turn prior requires a declared discrete route prior and consistent parameter-volume treatment. Until such a prior is justified, report every destination as a separate conditional family and do not pool them.

### Required geometry work

The shared domain currently provides WGS84 forward propagation but no WGS84 inverse azimuth or cross-track primitive. Tier 1 LNAV therefore needs:

- Robust current-position-to-waypoint course calculation.
- Immutable active-leg geometry.
- Cross-track and along-track distance.
- Explicit behavior at waypoint passage.
- A special geographic-pole representation because longitude is undefined at 90°S.
- Independent GeographicLib-style fixtures, including polar cases.

For McMurdo, use the proposal’s exact historical coordinate—not a live lookup of whichever modern Antarctic airfield currently uses a similar identifier. For the magnetic pole, freeze the coordinate and IGRF version at the accident epoch.

## 3-DoF/load/energy screen

Using upward-positive vertical velocity, constant horizontal ground speed, zero turn, and constant acceleration between the transmissions:

\[
a_z = \frac{w_2-w_1}{\Delta t},\qquad
\Delta h = \frac{w_1+w_2}{2}\Delta t
\]

\[
n_{\text{earth-up}}=1+\frac{a_z}{g},\qquad
\Delta e=\frac{V_2^2-V_1^2}{2}+g\Delta h
\]

|---|---:|
| Horizontal-speed proxy, median | 480.0 kt / 247.0 m/s |
| R600 vertical speed, median | −4,451 ft/min / −22.61 m/s |
| R1200 vertical speed, median | −14,995 ft/min / −76.17 m/s |
| Vertical-speed change | −10,543 ft/min |
| Mean earth-vertical acceleration | −0.6804 g |
| Ordinary-BFO-only acceleration SD | 0.0366 g |

The energy result means gravity supplies the increase in vertical kinetic energy while approximately 1.24 kJ/kg is dissipated. It does not require an energy source. That is a useful feasibility result, but the estimated \(L/D\) is not an aircraft measurement: the calculation substitutes ground speed for airspeed, omits wind, and assumes constant horizontal speed, zero roll, and lift normal to the flight path.

### Turn/load coupling

For a local turn rate \(\omega\), the transparent specific-load screen is:

\[
n_{\text{total}}
=
\sqrt{
\left(1+\frac{a_z}{g}\right)^2+
\left(\frac{V_h\omega}{g}\right)^2
}
\]

At the broad-search minimum:

- \(a_z=-0.6465g\)
- \(V_h\approx247\text{ m/s}\)
- \(\omega=6^\circ/\text{s}\)
- lateral acceleration \(=2.64g\)
- total specific load \(=2.66g\)
- specific-force tilt from earth-up \(=82.4^\circ\)

Thus the apparent improvement from −0.680 g to −0.647 g is bought by a very aggressive lateral maneuver at the search boundary.

For reference, the maximum turn rate at the same speed under several generic total-load ceilings would be:

| Generic total-load ceiling | Maximum turn rate |
|---:|---:|
| 1.0 g | 2.13°/s |
| 1.5 g | 3.32°/s |
| 2.5 g | 5.63°/s |
| 3.0 g | 6.78°/s |

Part 25 specifies a positive maneuver limit no lower than 2.5, while the normal structural safety factor is 1.5. Those are certification design rules, not the 9M-MRO operating envelope or proof that a particular out-of-control motion is attainable. [14 CFR 25.337](https://www.govinfo.gov/content/pkg/CFR-2013-title14-vol1/pdf/CFR-2013-title14-vol1-part25.pdf), [14 CFR 25.303](https://www.govinfo.gov/content/pkg/CFR-2023-title14-vol1/pdf/CFR-2023-title14-vol1-sec25-303.pdf)

I recommend 2.5 g only as a conservative generic screening threshold. Candidates above it should be labeled `outside_generic_limit_screen`, not assigned zero probability as though 2.5 g were a validated B777 cutoff.

Descending moves the aircraft farther from the elevated satellite line of sight and therefore increases BTO. It has the wrong sign to explain the observed decrease.

Using independent 63 and 43 µs errors, the change has an SD of 76.3 µs, making the 28.2 µs mismatch about 0.37 SD. Therefore:

- The BTO pair does not support rapid descent as the cause of the reduction.
- The reduction is also too small relative to the declared BTO uncertainties to reject the descent.
- It should remain a likelihood contribution, not a hard dynamic constraint.
- The result assumes independent correction errors; the repository has no R600/R1200 correction covariance.

ATSB reported that the anomalous R1200 offset’s specific cause could not be determined, reinforcing the need not to overinterpret the 20 µs difference. - Use air-relative velocity; if ground speed is substituted, record `velocity_basis=ground_proxy`.

- Generic load classification:

  - `within_generic_limit_screen`: \(n_{\text{total}}\le2.5\)
  - `outside_generic_limit_screen`: \(n_{\text{total}}>2.5\)
  - No B777 rejection probability without a validated envelope.

- In an unpowered hypothesis, require \(\Delta e\le0\). Positive mechanical-energy gain requires explicit thrust or environmental work.
- Report effective \(D-T\) and \(L/D\), but do not constrain them until a sourced aircraft envelope exists.
- Recalculate BTO using the propagated endpoint; report the altitude contribution separately.
- Time-step halving acceptance:

  - BTO change below 0.5 µs
  - BFO change below 0.1 Hz
  - velocity change below 0.1 m/s
  - event-time change below 0.1 s

### High-fidelity acceptance

A run may be labeled only `Boeing-case-feature-consistent`, not `aircraft-validated`, unless it has:

- Exact aircraft/engine/model/firmware identity.
- Complete initial state and system configuration.
- Explicit simulator database-validity flags.
- Reproduction of a public case with the same input deck.
- Limiting-case and time-step convergence.
- Model and input hashes and permitted publication/redistribution.

## Minimum high-fidelity input deck

ATSB says the manufacturer varied speed, fuel, electrical configuration, altitude, and turbulence. At minimum, a useful rerun requires:

- Time, WGS84 position, pressure/geometric altitude.
- Air-relative and ground-relative velocity vectors.
- Attitude quaternion, angle of attack, sideslip, and body rates.
- Aircraft mass, CG, inertia, and lateral fuel imbalance.
- Fuel quantity by tank, pickup geometry, unusable-fuel behavior under attitude and acceleration.
- Engine identity, thrust/spool/windmilling state, flameout and relight behavior.
- IDG/backup-generator dropout versus spool state.
- APU fuel availability, start state, generator-online timing, and retry behavior.
- AC buses, bus ties, RAT, battery, hydraulic availability, and actuator authority.
- Autopilot/autothrottle state, trim, and control-surface positions.
- Aerodynamic/control databases with valid-domain indicators.
- Temperature, pressure/density, 3-D wind, turbulence realization, and gravity.
- Integration method, time step, event interpolation, output filtering, model revision, and software/firmware versions.

ATSB’s public sequence supports approximately 60 seconds from dual-AC-bus loss to APU generator online and approximately 60 seconds from SDU power restoration to log-on request. It also distinguishes engine flameout, spool-down, generator dropout, bus loss, and SDU restoration, and warns that pitch and acceleration affect usable APU fuel.
